= Лабораторна робота №2
Класи. Типи зв'язків.

== Мета роботи

Отримати практичні навички розробки програм з використанням принципів
зв'язності об'єктів.

== Завдання

За допомогою класів та інтерфейсів додати до моделі з
{lab1-repo}[лабораторної роботи №1]
(поштова скринька) два з трьох типів зв'язків між об'єктами.

*Варіант 1* -- за основу взято тип зв'язку *"1. Композиція"*, як другий
(доповнюючий) тип реалізовано *"2. Агрегація"*. Наслідування
(4-й тип) вже присутнє в моделі з лаби 1 і в завданні до цієї
роботи окремо не рахується.

== Що додано порівняно з лабою 1

* Новий клас `MailboxKey` -- ключ від скриньки (композиція).
* Новий клас `PostOffice` -- поштове відділення (агрегація скриньок і
  листонош).
* Клас `Mailbox` доповнено полем `key` (композиція) та явним акцентом
  на існуючому зв'язку з `MailboxOwner` (агрегація).
* `Main` розширено демонстрацією обох зв'язків.

== Композиція: `Mailbox` \*-- `MailboxKey`

Композиція -- найсильніший тип зв'язку "ціле-частина": частина
створюється разом із цілим, не може існувати самостійно і знищується
разом із цілим.

Ключ (`MailboxKey`) створюється **всередині** конструктора `Mailbox`,
а не приймається ззовні:

[source,java]
----
public class Mailbox implements Notifiable {
    private final MailboxKey key;

    public Mailbox(String address, MailboxOwner owner) {
        this.address = address;
        this.owner = owner;
        this.key = new MailboxKey(address); // ключ народжується разом зі скринькою
    }
}
----

Клас `MailboxKey` навмисно має конструктор **пакетного рівня доступу**
(без модифікатора), тому створити ключ поза класом `Mailbox`
неможливо -- це підкреслює, що частина не має самостійного сенсу
поза цілим:

[source,java]
----
public class MailboxKey {
    private final String keyCode;

    MailboxKey(String mailboxAddress) { // package-private
        this.keyCode = "KEY-" + Integer.toHexString(mailboxAddress.hashCode()).toUpperCase();
    }
}
----

Якщо об'єкт `Mailbox` перестає існувати -- разом з ним "зникає" і
його `MailboxKey`: посилання на ключ ніде більше не зберігається.

== Агрегація

Агрегація -- слабший тип зв'язку "ціле-частина": частина створюється
незалежно від цілого, передається за посиланням і може існувати без
нього (а також належати кільком "цілим" одночасно чи бути перепризначеною).

=== `Mailbox` o-- `MailboxOwner`

Власник скриньки створюється поза класом `Mailbox` і передається в
конструктор за посиланням:

[source,java]
----
MailboxOwner owner = new MailboxOwner("Іван Петренко", "+380501112233");

Mailbox mailboxHome   = new Mailbox("вул. Хрещатик, 1, кв. 5", owner);
Mailbox mailboxOffice = new Mailbox("вул. Шевченка, 10, офіс 3", owner);
----

Один і той самий об'єкт `owner` агрегується одразу двома різними
скриньками -- це неможливо для композиції, але природно для агрегації:
власник існує незалежно і не "належить" виключно одній скриньці.

=== `PostOffice` o-- `Mailbox`, `PostOffice` o-- `Postman`

Новий клас `PostOffice` зберігає списки скриньок і листонош, отримані
ззовні через методи `registerMailbox()` / `hirePostman()`, а не
створені всередині себе:

[source,java]
----
public class PostOffice {
    private final List<Mailbox> mailboxes = new ArrayList<>();
    private final List<Postman> postmen = new ArrayList<>();

    public void registerMailbox(Mailbox mailbox) { mailboxes.add(mailbox); }
    public void hirePostman(Postman postman)     { postmen.add(postman); }

    public boolean unregisterMailbox(Mailbox mailbox) {
        return mailboxes.remove(mailbox);
    }
}
----

У демонстрації в `Main` скринька `mailboxOffice` видаляється зі
списку відділення (`unregisterMailbox`), але сам об'єкт продовжує
існувати і мати власника -- це і є доказ агрегації: знищення зв'язку
не знищує частину.

== Оновлена схема класів

[source]
----
postoffice
├── MailItem              (abstract)                     -- рівень 1
│   ├── Letter                                            -- рівень 2
│   │   └── RegisteredLetter implements Trackable         -- рівень 3
│   └── Parcel            implements Trackable            -- рівень 2
├── Mailbox                implements Notifiable
│     ├── *-- MailboxKey        (композиція, нове)
│     └── o-- MailboxOwner      (агрегація)
├── MailboxKey                                            (нове)
├── MailboxOwner
├── PostOffice                                            (нове)
│     ├── o-- Mailbox           (агрегація)
│     └── o-- Postman           (агрегація)
├── Postman
├── MailStatistics          (математична задача з лаби 1)
├── Main                    (демонстрація)
├── Trackable               <<interface>>
└── Notifiable              <<interface>>
----

Умовні позначення (нотація UML): `*--` -- композиція, `o--` --
агрегація.

== Висновок

У ході виконання лабораторної роботи до моделі поштової скриньки з
лаби 1 додано два типи зв'язків між об'єктами:

* *композицію* -- `Mailbox` та `MailboxKey`, де частина створюється
  разом з цілим і не існує окремо від нього;
* *агрегацію* -- `Mailbox` та `MailboxOwner`, а також `PostOffice` з
  `Mailbox` і `Postman`, де частини створюються незалежно, передаються
  за посиланням і продовжують існувати навіть після розірвання зв'язку
  з цілим.

Отримано практичні навички розрізнення та коректної реалізації різних
типів зв'язків між класами в Java (на противагу успадкуванню, яке вже
використовувалося в лабі 1).
